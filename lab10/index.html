0.2 O que você vai construir

Um script que recebe o nome ou o PID de um processo e, a cada intervalo, registra:

Coluna do CSVSignificadoDe onde vem
timestampHora da mediçãodate +%T
pidIdentificador do processopgrep ou argumento

mem% da memória físicatop

threadsNúmero de threads do processops (campo nlwp)

0.3 Pré-requisitos

  • Uma instância EC2 com Amazon Linux 2023 ligada (estado Running).
  • De preferência com 2 vCPUs ou mais (ex.: t3.small, t3.medium). Com 1 vCPU o lab funciona, mas a diferença entre threads e processos fica menos visível.
  • O security group da instância liberando a porta 22 (SSH).
  • Se for usar SSH: o arquivo da chave (.pem) baixado ao criar a instância.
Convenção desta páginaLinhas que começam com # dentro dos blocos são comentários e não precisam ser digitadas. Blocos com fundo claro e borda tracejada mostram a saída esperada. Os números de exemplo são de uma instância com 4 vCPUs; os seus podem ser diferentes.

3Conhecer os comandos que o script usa

Antes de automatizar, rode cada comando à mão para entender a saída. Use o seu próprio shell como alvo: o PID dele está na variável $$.

3.1 pgrep: achar o PID pelo nome

pgrep -a bash       # lista PID + comando de todos os "bash"

echo $$             # PID do seu shell atual

3.2 top em modo batch: %CPU e %MEM

As opções: -b = texto puro (sem tela interativa), -n 1 = uma atualização, -p = só esse PID. A última linha é a do processo; a coluna 9 é %CPU e a 10 é %MEM. Extraia as duas:

top -b -n 1 -p $$ | tail -1 | awk '{print $9, $10}'
0.0 0.1
Repare na linha de SwapInstâncias EC2 com Amazon Linux 2023 normalmente vêm sem swap (0.0 total). Se a memória acabar, o kernel aciona o OOM Killer direto, sem usar o disco. Tenha isso em mente ao escolher o tamanho da carga.

3.3 ps: RSS, threads e estado

ps -p $$ -o pid,comm,rss,nlwp,stat     # com cabeçalho
ps -p $$ -o rss=,nlwp=,stat=           # o "=" remove o cabeçalho
    PID COMMAND           RSS NLWP STAT
   2345 bash             4200    1 Ss
 4200    1 Ss

rss = memória física em KB · nlwp = number of light-weight processes, ou seja, nº de threads · stat = estado.

3.4 kill -0: o processo ainda existe?

kill -0 $$ && echo "existe"
kill -0 999999 2>/dev/null || echo "nao existe"

O sinal 0 não faz nada com o processo: só testa se ele existe e se você tem permissão sobre ele.

3.5 awk: comparar números com casas decimais

O Bash só compara inteiros; por isso usamos o awk para saber se 12.5 > 10:

awk -v c=12.5 -v l=10 'BEGIN{exit !(c>l)}' && echo "passou do limite"
✓ Checkpoint: você consegue obter, para o PID do seu shell, os valores de %CPU, %MEM, RSS, threads e estado com um comando cada.

5.3 O código

#!/usr/bin/env bash
# monitor.sh - mede CPU, memoria e threads de um processo e salva em CSV
# Uso: ./monitor.sh <PID|nome> [intervalo_s] [amostras] [limite_cpu]
export LC_ALL=C                      # ponto decimal (evita "12,5" no CSV)
ALVO=$1; INTERVALO=${2:-1}; AMOSTRAS=${3:-30}; LIMITE=${4:-80}
[ -z "$ALVO" ] && { echo "Uso: $0 <PID|nome> [intervalo] [amostras] [limite]"; exit 1; }

# 1) Descobrir o PID
if [[ "$ALVO" =~ ^[0-9]+$ ]]; then PID=$ALVO; else PID=$(pgrep -o "$ALVO"); fi
[ -z "$PID" ] && { echo "Processo '$ALVO' nao encontrado"; exit 1; }

# 2) Preparar o arquivo de saida
NOME=$(ps -p "$PID" -o comm=)
ARQ="medicoes_${NOME}_$(date +%Y%m%d_%H%M%S).csv"
echo "timestamp,pid,cpu,mem,rss_kb,threads,estado" > "$ARQ"
echo "Monitorando $NOME (PID $PID) -> $ARQ"

# 3) Laco de medicoes
for ((i=1; i<=AMOSTRAS; i++)); do
  kill -0 "$PID" 2>/dev/null || { echo "Processo terminou"; break; }
  read CPU MEM <<< "$(top -b -n 1 -p "$PID" | tail -1 | awk '{print $9, $10}')"
  read RSS THR EST <<< "$(ps -p "$PID" -o rss=,nlwp=,stat=)"
  echo "$(date +%T),$PID,$CPU,$MEM,$RSS,$THR,$EST" >> "$ARQ"

  # 4) Gerenciar: alerta se passar do limite
  if awk -v c="$CPU" -v l="$LIMITE" 'BEGIN{exit !(c>l)}'; then
    echo "[ALERTA] $(date +%T) CPU=$CPU% > $LIMITE%" | tee -a alertas.log
  fi
  sleep "$INTERVALO"
done

# 5) Resumo estatistico
echo "--- Resumo ---"
awk -F, 'NR>1 {c+=$3; m+=$5; n++; if($3>mx) mx=$3; if($6>t) t=$6}
  END {printf "Amostras: %d\n", n
       printf "CPU media: %.1f%%  max: %.1f%%\n", c/n, mx
       printf "RSS medio: %.0f KB\nMax threads: %d\n", m/n, t}' "$ARQ"
Baixar monitor.sh

8Criar o programa de carga (substitui o sysbench)

Um shell parado não mostra nada interessante. Precisamos de um programa que ocupe CPU e memória de forma controlada. É isso que o carga.c faz: cada trabalhador fica fazendo contas por N segundos, ocupando um núcleo inteiro.

8.1 Baixar o código

cd ~/lab10
curl -O https://dcpc-cesar-school.github.io/projeto-integrador3-26.2/lab10/carga.c
Baixar carga.c 
/* carga.c - gera carga de CPU e memoria usando THREADS ou PROCESSOS.
 * Substitui o sysbench (threads) e o stress-ng (processos) no Lab 10.
 *
 * Compilar (o mesmo codigo vira dois programas):
 *   gcc -O2 -pthread -o carga_threads carga.c
 *   gcc -O2 -pthread -o carga_procs   carga.c
 * O modo e escolhido pelo nome do programa: se o nome contem "procs",
 * cria processos filhos (fork); senao, cria threads (pthread_create).
 *
 * Uso:  ./carga_threads [n] [segundos] [mb]
 *       ./carga_procs   [n] [segundos] [mb]
 * Ex.:  ./carga_threads 4 90 256   -> 1 processo com 4 threads de trabalho
 *       ./carga_procs   4 90 256   -> 1 processo pai + 4 processos filhos
 */
#include <pthread.h>
#include <stdio.h>
#include <stdlib.h>
#include <string.h>
#include <sys/wait.h>
#include <time.h>
#include <unistd.h>

static int segundos = 60;

static void *trabalho(void *arg) {          /* ocupa 1 nucleo ate o tempo acabar */
    (void)arg;
    volatile double x = 0;
    time_t fim = time(NULL) + segundos;
    while (time(NULL) < fim)
        for (int i = 1; i < 1000000; i++) x += 1.0 / i;
    return NULL;
}

int main(int argc, char *argv[]) {
    int procs = strstr(argv[0], "procs") != NULL;
    int n     = argc > 1 ? atoi(argv[1]) : 4;
    segundos  = argc > 2 ? atoi(argv[2]) : 60;
    int mb    = argc > 3 ? atoi(argv[3]) : 0;
    if (n < 1 || segundos < 1 || mb < 0) {
        fprintf(stderr, "Uso: %s [n>=1] [segundos>=1] [mb>=0]\n", argv[0]);
        return 1;
    }

    if (mb > 0) {                            /* aloca e escreve -> aparece no RSS */
        size_t bytes = (size_t)mb * 1024 * 1024;
        char *buf = malloc(bytes);
        if (!buf) { perror("malloc"); return 1; }
        memset(buf, 1, bytes);
    }
    printf("%s: modo=%s n=%d tempo=%ds mem=%dMB pid=%d\n", argv[0],
           procs ? "processos" : "threads", n, segundos, mb, getpid());
    fflush(stdout);

    if (procs) {
        for (int i = 0; i < n; i++)
            if (fork() == 0) { trabalho(NULL); _exit(0); }
        while (wait(NULL) > 0) ;             /* o pai so espera os filhos */
    } else {
        pthread_t t[n];
        for (int i = 0; i < n; i++) pthread_create(&t[i], NULL, trabalho, NULL);
        for (int i = 0; i < n; i++) pthread_join(t[i], NULL);
    }
    return 0;
}

8.2 O que observar no código

TrechoO que faz
trabalho()Laço de contas que ocupa um núcleo até o tempo acabar. volatile impede o compilador de “otimizar” e apagar as contas.
malloc + memsetReserva mb megabytes e escreve neles. Só a memória escrita vira RSS; memória só reservada aparece apenas no VIRT.
pthread_create / pthread_joinCria N threads dentro do mesmo processo e espera todas terminarem.
fork() / wait()Cria N processos filhos, cada um com seu próprio PID. O pai só espera.
strstr(argv[0], "procs")Escolhe o modo pelo nome do executável. Assim, cada modo aparece com um nome diferente no top e no CSV.

8.3 Compilar

gcc -O2 -pthread -o carga_threads carga.c

-pthread liga a biblioteca de threads; -O2 ativa otimizações; -o define o nome do executável.

8.4 Subir a carga em segundo plano

Escolha o número de threads igual ao número de vCPUs e uma memória bem abaixo da disponível (free -m). O & no final devolve o terminal:

# N threads (= nº de vCPUs) por 90 s, usando 256 MB de RAM
./carga_threads $(nproc) 90 256 > /dev/null &
[1] 4211

[1] é o número do job e 4211 o PID. Confira:

jobs                       # jobs em segundo plano deste terminal
pgrep -a carga_threads     # PID e linha de comando
ps -T -p $(pgrep carga_threads)   # uma linha por thread (coluna SPID)
Dica: veja as threads ao vivoAbra um segundo terminal (outra aba do Instance Connect ou outra janela de SSH) e rode top -H -p $(pgrep carga_threads). Cada linha é uma thread. Saia com q.
Cuidado com a memóriaA instância não tem swap. Se você pedir mais memória do que existe, o processo morre pelo OOM Killer (confira com sudo dmesg | grep -i oom). Comece com 256 MB.

9Executar o monitor

Formato: ./monitor.sh <alvo> <intervalo_s> <amostras> <limite_cpu>

# carga_threads, 1 amostra/s, 30 amostras, alerta acima de 150%
./monitor.sh carga_threads 1 30 150
Monitorando carga_threads (PID 4211) -> medicoes_carga_threads_20261112_190201.csv
[ALERTA] 19:02:01 CPU=398.0% > 150%
[ALERTA] 19:02:02 CPU=397.3% > 150%
...
--- Resumo ---
Amostras: 30
CPU media: 395.8%  max: 399.0%
RSS medio: 263400 KB
Max threads: 5
Por que passa de 100%?No top, 100% = um núcleo inteiro. Quatro threads em quatro vCPUs somam ~400%. Com 2 vCPUs, o máximo será ~200%.
Por que 5 threads e não 4?As 4 threads de trabalho + a thread principal (o main, que fica no pthread_join esperando).
Por que o RSS deu ~256 MB?São os 256 MB escritos pelo memset, mais alguns KB do próprio programa.

Experimente variar os parâmetros (suba a carga de novo se ela já tiver terminado):

./monitor.sh carga_threads 2 10 300    # 1 amostra a cada 2 s, limite maior
./monitor.sh 4211 1 5                  # usando o PID em vez do nome
Instâncias t2/t3 (burstable)Essas instâncias usam créditos de CPU. Se os créditos acabarem durante o lab, o %CPU máximo cai com o tempo. Se isso acontecer, anote no relatório: é um efeito real da nuvem, e não um erro do script.

CExperimentos de SO e perguntas obrigatórias

Três experimentos curtos (cerca de 15 minutos no total) que revelam o que o kernel faz por baixo dos números do monitor. Depois deles, responda às perguntas Q1 a Q8 no relatório.

C1 · Chamadas de sistema: como nascem threads e processos

O strace intercepta as chamadas que o programa faz ao kernel. Vamos ver qual chamada cria cada thread e cada processo:

cd ~/lab10
strace -f -e trace=clone,clone3 ./carga_threads 2 1 2>&1 | grep -o 'flags=[A-Z_|]*' | head -1
strace -f -e trace=clone,clone3 ./carga_procs   2 1 2>&1 | grep -o 'flags=[A-Z_|]*' | head -1
flags=CLONE_VM|CLONE_FS|CLONE_FILES|CLONE_SIGHAND|CLONE_THREAD|CLONE_SYSVSEM|CLONE_SETTLS|CLONE_PARENT_SETTID|CLONE_CHILD_CLEARTID
flags=CLONE_CHILD_CLEARTID|CLONE_CHILD_SETTID|SIGCHLD

No Linux, pthread_create e fork usam a mesma família de chamadas (clone/clone3). O que muda são as flags: CLONE_VM = usar o mesmo espaço de endereçamento; CLONE_THREAD = ficar no mesmo processo (mesmo PID). Sem essas flags, nasce um processo novo, com a memória copiada sob demanda.

C2 · Memória virtual: VIRT × RSS

./carga_threads 4 60 64 > /dev/null &
P=$!; sleep 1
grep -E 'VmSize|VmRSS|Threads' /proc/$P/status
pkill carga_threads
VmSize:	  101104 kB
VmRSS:	   67284 kB
Threads:	5

VmSize (o VIRT do top) é tudo que o processo reservou no espaço de endereçamento; VmRSS é o que está de fato na RAM. A diferença (~33 MB) vem principalmente das pilhas das 4 threads: cada uma reserva 8 MB, mas só usa poucas páginas. O kernel só entrega memória física quando a página é tocada (paginação sob demanda).

C3 · Copy-on-write no fork

free -m | awk '/Mem:/{print "usada antes:", $3, "MB"}'
./carga_procs 4 30 256 > /dev/null &
sleep 2
ps -o pid,ppid,rss,comm -C carga_procs
free -m | awk '/Mem:/{print "usada depois:", $3, "MB"}'
pkill carga_procs
usada antes: 158 MB
    PID    PPID   RSS COMMAND
   5120    2345 263860 carga_procs
   5122    5120 262328 carga_procs
   5123    5120 262328 carga_procs
   5124    5120 262328 carga_procs
   5125    5120 262328 carga_procs
usada depois: 418 MB

Somando o RSS dos 5 processos dá ~1,3 GB, mas a memória usada da máquina subiu só ~260 MB. Depois do fork, pai e filhos compartilham as mesmas páginas físicas; o kernel só faz a cópia de uma página quando alguém escreve nela (copy-on-write). O RSS conta páginas compartilhadas em cada processo.

★Desafio, entrega e avaliação

Estenda o script para gerenciar o processo, não só medir:

  1. Proteção de memória: se o RSS passar de N MB, envie kill -15 "$PID" e registre o evento em alertas.log. Teste com ./carga_threads 1 120 600 e um limite de 500 MB, sempre abaixo da memória livre (free -m). É a versão “controlada” do OOM Killer que o projeto pede.
  2. Prioridade: aplique renice +10 -p "$PID" quando a CPU passar do limite. Confira a coluna NI no top.
  3. Contexto do sistema: acrescente ao CSV o load average de 1 min (cut -d' ' -f1 /proc/loadavg) e a memória disponível (free -m | awk '/Mem:/{print $7}').
  4. Somar os filhos: faça o monitor somar a CPU do pai e de todos os filhos (dica: pgrep -P "$PID" lista os filhos).
  5. Comparação: preencha a tabela da seção 11.2 e explique as diferenças.
