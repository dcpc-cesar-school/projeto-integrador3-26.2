0Antes de começar

O que você vai construir: um script que recebe o nome ou o PID de um processo e, a cada intervalo, registra:

Coluna do CSVSignificadoDe onde vem
timestampHora da mediçãodate +%T
pidIdentificador do processopgrep ou argumento
cpu% de CPU no último intervalo (100% = 1 núcleo)top
mem% da memória físicatop
rss_kbMemória física residente, em KBps
threadsNúmero de threads do processops (campo nlwp)
estadoR executando, S dormindo, D esperando E/S, Z zumbi…ps (campo stat)

Pré-requisitos: uma máquina com Red Hat Enterprise Linux (os comandos também funcionam em Rocky, AlmaLinux, CentOS Stream e Fedora) e um usuário com permissão de sudo.

Convenção desta páginaLinhas que começam com # dentro dos blocos são comentários — não precisam ser digitadas. Blocos com fundo claro e borda tracejada mostram a saída esperada.

3Conhecer os comandos que o script usa

Antes de automatizar, rode cada comando à mão para entender a saída. Use o seu próprio shell como alvo — o PID dele está na variável $$.

3.1 pgrep — achar o PID pelo nome

pgrep -a bash       # lista PID + comando de todos os "bash"
pgrep -o bash       # só o mais antigo (-o = oldest)
echo $$             # PID do seu shell atual

3.2 top em modo batch — %CPU e %MEM

top -b -n 1 -p $$
top - 19:10:02 up  1:02,  1 user,  load average: 0.00, 0.01, 0.00
Tasks:   1 total,   0 running,   1 sleeping,   0 stopped,   0 zombie
%Cpu(s):  0.3 us,  0.2 sy,  0.0 ni, 99.5 id,  0.0 wa,  0.0 hi,  0.0 si,  0.0 st
MiB Mem :   7843.2 total,   6012.4 free,   1101.7 used,    729.1 buff/cache
MiB Swap:   2048.0 total,   2048.0 free,      0.0 used.   6489.3 avail Mem

    PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM     TIME+ COMMAND
   1234 aluno     20   0  224108   5340   3412 S   0.0   0.1   0:00.03 bash

As opções: -b = texto puro (sem tela interativa), -n 1 = uma atualização, -p = só esse PID. A última linha é a do processo; a coluna 9 é %CPU e a 10 é %MEM. Extraia as duas:

top -b -n 1 -p $$ | tail -1 | awk '{print $9, $10}'
0.0 0.1

3.3 ps — RSS, threads e estado

ps -p $$ -o pid,comm,rss,nlwp,stat     # com cabeçalho
ps -p $$ -o rss=,nlwp=,stat=           # o "=" remove o cabeçalho
    PID COMMAND           RSS NLWP STAT
   1234 bash             5340    1 Ss
 5340    1 Ss

rss = memória física em KB · nlwp = number of light-weight processes, ou seja, nº de threads · stat = estado.

3.4 kill -0 — o processo ainda existe?

kill -0 $$ && echo "existe"
kill -0 999999 2>/dev/null || echo "nao existe"

O sinal 0 não faz nada com o processo: só testa se ele existe e se você tem permissão sobre ele.

3.5 awk — comparar números com casas decimais

O Bash só compara inteiros; por isso usamos o awk para saber se 12.5 > 10:

awk -v c=12.5 -v l=10 'BEGIN{exit !(c>l)}' && echo "passou do limite"
✓ Checkpoint: você consegue obter, para o PID do seu shell, os valores de %CPU, %MEM, RSS, threads e estado com um comando cada.

5.2 O código

#!/usr/bin/env bash
# monitor.sh - mede CPU, memoria e threads de um processo e salva em CSV
# Uso: ./monitor.sh <PID|nome> [intervalo_s] [amostras] [limite_cpu]
export LC_ALL=C                      # ponto decimal (evita "12,5" no CSV)
ALVO=$1; INTERVALO=${2:-1}; AMOSTRAS=${3:-30}; LIMITE=${4:-80}
[ -z "$ALVO" ] && { echo "Uso: $0 <PID|nome> [intervalo] [amostras] [limite]"; exit 1; }

# 1) Descobrir o PID
if [[ "$ALVO" =~ ^[0-9]+$ ]]; then PID=$ALVO; else PID=$(pgrep -o "$ALVO"); fi
[ -z "$PID" ] && { echo "Processo '$ALVO' nao encontrado"; exit 1; }

# 2) Preparar o arquivo de saida
NOME=$(ps -p "$PID" -o comm=)
ARQ="medicoes_${NOME}_$(date +%Y%m%d_%H%M%S).csv"
echo "timestamp,pid,cpu,mem,rss_kb,threads,estado" > "$ARQ"
echo "Monitorando $NOME (PID $PID) -> $ARQ"

# 3) Laco de medicoes
for ((i=1; i<=AMOSTRAS; i++)); do
  kill -0 "$PID" 2>/dev/null || { echo "Processo terminou"; break; }
  read CPU MEM <<< "$(top -b -n 1 -p "$PID" | tail -1 | awk '{print $9, $10}')"
  read RSS THR EST <<< "$(ps -p "$PID" -o rss=,nlwp=,stat=)"
  echo "$(date +%T),$PID,$CPU,$MEM,$RSS,$THR,$EST" >> "$ARQ"

  # 4) Gerenciar: alerta se passar do limite
  if awk -v c="$CPU" -v l="$LIMITE" 'BEGIN{exit !(c>l)}'; then
    echo "[ALERTA] $(date +%T) CPU=$CPU% > $LIMITE%" | tee -a alertas.log
  fi
  sleep "$INTERVALO"
done

# 5) Resumo estatistico
echo "--- Resumo ---"
awk -F, 'NR>1 {c+=$3; m+=$5; n++; if($3>mx) mx=$3; if($6>t) t=$6}
  END {printf "Amostras: %d\n", n
       printf "CPU media: %.1f%%  max: %.1f%%\n", c/n, mx
       printf "RSS medio: %.0f KB\nMax threads: %d\n", m/n, t}' "$ARQ"
Baixar monitor.sh

6Entender o script linha a linha

TrechoO que faz
#!/usr/bin/env bashShebang: diz ao sistema que o arquivo deve ser executado pelo Bash.
export LC_ALL=CForça o idioma “C”: números saem com ponto (12.5), não vírgula — senão o CSV quebra.
ALVO=$1$1, $2… são os argumentos passados na linha de comando.
${2:-1}Usa o 2º argumento; se não foi passado, usa o valor padrão 1.
[ -z "$ALVO" ] && {…; exit 1; }Se o alvo está vazio (-z), mostra o uso e sai com código de erro 1.
[[ "$ALVO" =~ ^[0-9]+$ ]]Expressão regular: o alvo é só dígitos? Então já é um PID.
PID=$(pgrep -o "$ALVO")$( … ) executa um comando e guarda a saída na variável.
ps -p "$PID" -o comm=Nome curto do processo, usado no nome do arquivo.
date +%Y%m%d_%H%M%SData e hora no nome do CSV → cada execução gera um arquivo novo.
> e >>> cria/sobrescreve (cabeçalho); >> acrescenta no final (cada amostra).
for ((i=1; i<=AMOSTRAS; i++))Laço no estilo C: repete AMOSTRAS vezes.
kill -0 … || { …; break; }Se o processo morreu, para o laço.
read CPU MEM <<< "…"Here-string: separa a saída “98.0 1.2” em duas variáveis.
tee -a alertas.logMostra o alerta na tela e acrescenta no arquivo de log.
sleep "$INTERVALO"Espera N segundos até a próxima amostra.
awk -F, 'NR>1 {…} END {…}'Lê o CSV (separador vírgula), pula o cabeçalho (NR>1), acumula somas e máximos; no END imprime médias.

8Subir uma carga para monitorar

Um shell parado não mostra nada interessante. Vamos rodar um programa que ocupa CPU em segundo plano (o & no final devolve o terminal):

# 4 threads ocupando CPU por 90 segundos; a saída vai para o "lixo"
sysbench cpu --threads=4 --time=90 run > /dev/null &
[1] 4211

[1] é o número do job e 4211 o PID. Confira:

jobs                 # jobs em segundo plano deste terminal
pgrep -a sysbench    # PID e linha de comando
Dica: veja as threads ao vivoAbra um segundo terminal e rode top -H -p $(pgrep sysbench). Cada linha é uma thread (coluna PID mostra o TID). Saia com q.

9Executar o monitor

Formato: ./monitor.sh <alvo> <intervalo_s> <amostras> <limite_cpu>

# sysbench, 1 amostra/s, 30 amostras, alerta acima de 150%
./monitor.sh sysbench 1 30 150
Monitorando sysbench (PID 4211) -> medicoes_sysbench_20261029_190201.csv
[ALERTA] 19:02:01 CPU=398.0% > 150%
[ALERTA] 19:02:02 CPU=397.3% > 150%
...
--- Resumo ---
Amostras: 30
CPU media: 395.8%  max: 399.0%
RSS medio: 5120 KB
Max threads: 5
Por que passa de 100%?No top, 100% = um núcleo inteiro. Quatro threads em quatro núcleos somam ~400%. Se sua máquina tem 2 núcleos (nproc), o máximo será ~200%.
Por que 5 threads e não 4?As 4 threads de trabalho + a thread principal do processo.

Experimente variar os parâmetros:

./monitor.sh sysbench 2 10 300     # 1 amostra a cada 2 s, limite maior
./monitor.sh 4211 1 5               # usando o PID em vez do nome

11Comparar threads × processos

O sysbench cria threads; o stress-ng cria processos (workers). Rode o stress-ng e monitore:

stress-ng --cpu 2 --vm 1 --vm-bytes 512M --timeout 90s &
sleep 2
pstree -p $(pgrep -o stress-ng)        # árvore: 1 pai + vários filhos
ps -T -p $(pgrep -o stress-ng)         # threads do processo pai
./monitor.sh stress-ng 1 20 50

Repare: o monitor mede só o processo pai, que quase não usa CPU — o trabalho está nos filhos. Para monitorar um filho, use o PID dele (veja no pstree).

11.1 Alternativa sem sysbench: programa com threads em Python

cat > carga_threads.py <<'EOF'
import threading, time
def trabalho():
    fim = time.time() + 90
    while time.time() < fim:
        sum(i*i for i in range(10000))
for _ in range(4):
    threading.Thread(target=trabalho).start()
EOF
python3 carga_threads.py &
./monitor.sh python3 1 20 50

Você verá 5 threads, mas %CPU perto de 100% (não 400%): o Python executa uma thread por vez por causa do GIL. Boa pergunta para discutir em sala!

Passo 1 — Juntar as medições em uma planilha de resultados

Cada execução do monitor gerou um CSV. O comando abaixo junta todos em um só arquivo e acrescenta uma coluna com o nome do programa:

cd ~/lab09
{
  echo "programa,timestamp,pid,cpu,mem,rss_kb,threads,estado"
  for f in medicoes_*.csv; do
    p=$(echo "$f" | cut -d_ -f2)          # sysbench, stress-ng, python3…
    tail -n +2 "$f" | sed "s/^/$p,/"      # pula o cabeçalho e põe o programa na frente
  done
} > resultados_lab09.csv

Cole este prompt (ajuste o que estiver entre colchetes):

- alertas.log: alertas de CPU acima do limite configurado.

★Desafio e entrega

Estenda o script para gerenciar o processo, não só medir:

  1. Proteção de memória: se o RSS passar de N MB, envie kill -15 "$PID" e registre o evento em alertas.log. Teste com stress-ng --vm 1 --vm-bytes 1G.
  2. Prioridade: aplique renice +10 -p "$PID" quando a CPU passar do limite. Confira a coluna NI no top.
  3. Contexto do sistema: acrescente ao CSV o load average de 1 min (cut -d' ' -f1 /proc/loadavg) e a memória disponível (free -m | awk '/Mem:/{print $7}').
  4. Gráfico: plote o CSV em planilha ou com gnuplot (sudo dnf install -y gnuplot).
  5. Comparação: preencha a tabela da seção 11 e explique as diferenças.
